# 本地知识库与 RAG

LunarShroud 的知识库不是“把文档拿去训练模型”。文档只在本地经历一次
**提取 → 分块 → 向量化 → 建索引**；对话时只对当前问题做一次向量化检索。
模型权重不会被修改，原始文件也不会离开本机。

## 使用流程

1. 侧栏进入 **知识库**，新建一个库并选择嵌入模型（GGUF）。
2. 添加本机文件或文件夹。支持文本/代码、HTML、PDF、DOCX。
3. 扫描版 PDF 需要同时填写 OCR 主模型和配套 `mmproj`。纯文本 PDF 不会启动 OCR。
4. 可选填写重排模型并启用重排；它只处理检索候选，不参与文档建索引。
5. 等索引完成后，在 **Chat** 顶栏选择该知识库。回答会带 `[1]` 编号，消息下方的
   “引用来源”可展开查看文件、页码和原文片段。
6. 换嵌入模型或分块参数后，点 **全量重建**。只新增/修改文件时点 **更新索引** 即可。

## 分层资源策略

索引被拆成两个阶段，避免视觉模型、投影文件和嵌入模型同时常驻：

| 阶段 | 会启动什么 | 结束后 |
|---|---|---|
| 提取 | 文本/PDF/DOCX 解析；只有扫描页才启动 OCR | OCR 服务卸载，页面文本按文件 SHA-256 缓存 |
| 嵌入 | 嵌入服务 | 服务进入空闲窗口，10 分钟后自动卸载；也可手动卸载 |
| 检索 | 嵌入服务（问题向量化） | 同上；启用重排时额外启动重排服务 |

对话模型、嵌入模型和重排模型是不同职责。知识库服务通过现有
`ProcessManager` 启动，因此沿用同一套端口预留、能力探测、日志、环境清洗和
Job Object 回收，不会绕过启动器直接拉起进程。

## 检索与引用

- SQLite 保存片段与 float32 向量；检索用余弦相似度与 FTS5 三元组关键词做
  Reciprocal Rank Fusion。法条编号、人名等精确词即使嵌入分数不高也能被带回。
- 默认每个问题注入最多 6 个片段，约 6,000 字符；可在库设置中调整 top-k、最低
  相似度和分块参数。
- 引用通过响应头 `X-LunarShroud-Sources`（base64url JSON）返回，并保存在消息
  `stats.sources` 中；重新加载会话和 Markdown 导出都会保留。
- 如果所选知识库没有命中内容，后端返回 `X-LunarShroud-Knowledge: miss`，前端明确
  提示“未引用资料”，不会假装检索成功。

### 实测检索质量（2026-10-23）

在一个真实法律库上量化：8 部法律法规 / PDF+DOCX / 377 片段 / 68,268 字符，
**21 道**人工标注问题（定义、条号、日期、跨文档、纯词法、英文问句）+
**10 道**语料库答不了的对照题；每题的 gold 先对索引正文校验确实存在才纳入统计。
模型是 Qwen3-Embedding-0.6B-Q8_0 与 Qwen3-Reranker-0.6B-Q8_0。

| 配置 | hit@1 | hit@3 | hit@5 | MRR | ms/问 |
| --- | --- | --- | --- | --- | --- |
| 仅向量 | 33% | 52% | 57% | 0.440 | 350 |
| 混合（RRF） | 47% | 66% | 76% | 0.610 | 386 |
| 混合 + 文档限额 | 47% | **76%** | **80%** | 0.612 | 385 |
| 混合 + 文档限额 + 重排（**默认路径**） | **76%** | **95%** | **95%** | **0.841** | 1033 |

复现（会自行拉起两个 llama-server，跑完关闭）：

```powershell
$env:LUNARSHROUD_LLAMA_SERVER = "C:\path\to\llama-server.exe"
$env:LUNARSHROUD_TEST_EMBEDDING = "C:\path\to\embedding.gguf"
$env:LUNARSHROUD_TEST_RERANK = "C:\path\to\reranker.gguf"
$env:LUNARSHROUD_TEST_KB = "<knowledge base id>"
python tools/eval_knowledge_retrieval.py
```

题目与 gold 都在脚本里；gold 先对索引正文校验存在，不存在的题会直接中止而不是
算成 miss。

三个结论值得单独记：

- 修好词法分支之前，**混合检索的排序与纯向量逐条相同**：`search_fts` 当时把整句
  问话包成一个 FTS5 短语，题里词法命中 0 次。拆成 3-gram 子句之后才有上表
  混合那一行的增益（见 `AGENTS.md` §2.28）。
- **重排是最大的单一杠杆**（hit@1 47%→76%，MRR 0.61→0.84），代价约 3 倍延迟；
  所以带重排的库和不带的库不是一个体验档位。
- **文档限额**（每篇最多占 2 个短名单槽位）对不带重排的路径是白捡的提升：
  hit@3 66%→76%、hit@5 76%→80%，hit@1 不变。带重排时两者等价。

被实测**否掉**的两个方案（别再试）：

- **按"第X条"边界切块**。听起来最"法律"，实测把不带重排的混合 hit@1 从 52% 打到
  35%：小条块在两个召回臂里都被稀释。保留原窗口切块、只把条号写进 chunk
  `heading`（引用里就显示《法名》第N页 · 第十七条），零成本拿到同一份引用可读性。
- **用"最低相关度"过滤无关问题**。21 道正解题的 top-1 分数最低到 **0.0**，而 10 道
  语料库答不了的题 top-1 最高到 **0.575** —— 区间完全重叠，任何经验阈值都会同时
  造成漏检和放行。要做得先有校准依据，目前 rerank 分数不具备跨查询可比性。

尚未解决、也没有粉饰的部分：

- 精确条号查询（"个人信息保护法 第十七条"）在四种配置里都没回到第一位。文档限额
  缓解了压制，但 161 片段的条例仍然占优；下一步是查询意图识别（识别出"只要某部法
  的第N条"时做元数据过滤），而不是继续调融合权重。
- 不能靠“最低分”过滤无关问题。实测三个语料库答不了的问句，重排 top-1 分数
  0.300 / 0.336 / **0.574**，而部分正确命中低到 0.0 和 0.44 —— 分数区间重叠，
  任何经验阈值都会同时造成漏检和放行。**在没有校准依据之前不要加这个阈值。**
- PDF 的"丢字"**不在解析器也不在 OCR**：这批法律 PDF 是浏览器打印件，换行处右侧
  被裁掉，缺的字在文件里根本不存在（把页面渲染成 PNG 逐像素核对过：
  "…完整地向个 / 列事项：" 就是纸面上的样子）。pypdf 与 pypdfium2 的文本层均为
  0 字符（纯扫描件），渲染倍率 2/3/4 与三种 OCR 提示词的识别结果逐字相同。
  因此产品侧的做法是**如实标注**：`kind == 'pdf-ocr'` 的文档在知识库列表带 OCR
  徽标，聊天引用同样带徽标并提示"尽力识别结果，请核对原件"。要真正修好这类
  资料，只能换干净的源文件（例如国家法律法规数据库的导出）后重建索引。

## 容量与边界

- 每个知识库默认上限：2,000 个文件、512 MiB 原始资料、20,000 个片段。
- 达到上限时返回可读错误并保留旧索引，不静默删除用户资料。
- 当前一个对话只绑定一个知识库。
- OCR 质量取决于模型、PDF 渲染和版式。法律文本上线前应对关键页做人工抽检；
  应用不会把 OCR 结果描述成逐字保证。
- 知识库索引文件为 `data/knowledge.db`，已纳入备份/恢复。源文件本身不复制进
  备份，恢复后路径必须仍在本机可访问。

## 故障恢复

- 上次进程退出时处于 `queued`/`indexing` 的文档会在启动时收口为错误，避免历史页
  永远显示“索引中”。
- 已完成的 OCR 页面和整篇提取结果分别按内容哈希缓存；重新嵌入不会重复 OCR。
- 损坏的 `knowledge.db` 会连同 `-wal`/`-shm` 隔离为 `.corrupt*` 后重建，不影响
  聊天与启动器主功能。
